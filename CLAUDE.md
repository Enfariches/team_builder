# TeamBuilder

Сервис формирования студенческих проектных команд. Преподаватель создаёт
пространство, задаёт правила состава (размер команды + роли с квотами),
рассылает инвайт-ссылку. Студенты вступают с анкетой компетенций. По кнопке
или по таймеру запускается распределение по командам.

Монорепозиторий: бэкенд на Go, фронтенд отдельной папкой (пока заготовка),
общий контракт OpenAPI. Запуск — только Docker.

---

## Стек

| Слой | Выбор |
|---|---|
| Язык | Go 1.23+ |
| HTTP | echo |
| БД | PostgreSQL 16 |
| Доступ к БД | pgx + sqlc (запросы пишутся на SQL, типы генерируются) |
| Миграции | goose |
| Контракт | OpenAPI 3.0.3 + oapi-codegen (strict server) |
| Логи | log/slog, JSON |
| Пароли | Argon2id (`golang.org/x/crypto/argon2`) |
| Токены | JWT, access 30 мин + refresh в httpOnly cookie |
| Тесты | стандартный `testing` + testcontainers-go |
| Реалтайм | SSE (не WebSocket — трафик односторонний) |

Не добавлять без явной просьбы: ORM (GORM, ent), DI-фреймворки (wire, fx),
Redis, Kafka, gRPC, инструменты управления монорепо (Nx, Turborepo, Bazel).
Проект маленький, накладные расходы этих инструментов здесь превышают пользу.

```

/backend

  /internal
    /auth                  # токены, хеши, middleware RequireAuth
    /user                  # профиль
    /form                  # анкеты компетенций
    /split                 # пространства, роли с квотами, статусы, инвайты
    /member                # участие, вступление по инвайту
    /distribution          # алгоритм, прогоны, публикация результата
    /team                  # команды, выгрузка
    /platform              # общее: БД, логгер, конфиг, HTTP-ошибки, middleware
    /api/gen               # сгенерированный oapi-codegen код (не править руками)
  /migrations              # goose, формат NNNN_name.sql
```

### Модули — вертикальные, не горизонтальные

Уровни (handler → service → repository) живут **внутри** модуля. Нет общих
пакетов `handlers/`, `services/`, `repositories/` на весь проект.

Состав каждого модуля:

```
/split
  domain.go       # типы предметной области и их инварианты, без внешних зависимостей
  service.go      # бизнес-логика; работает с domain и интерфейсами из port.go
  repository.go   # SQL только для таблиц этого модуля
  handler.go      # HTTP: разбор запроса, вызов service, маппинг в DTO
  port.go         # интерфейсы ЧУЖИХ модулей, которые нужны этому
```

## Правила границ между модулями

Это главное, что держит проект в порядке. Нарушение здесь обходится дороже
любого другого.

1. **Модуль никогда не обращается к таблицам другого модуля.** `distribution`
   не пишет `SELECT ... FROM members`. Он просит данные у `member.Service`.

2. **Зависимость объявляется у потребителя, а не у поставщика.** Модулю
   `distribution` нужны кандидаты — он объявляет у себя в `port.go`:

   ```go
   // internal/distribution/port.go
   type MemberProvider interface {
       ListCandidates(ctx context.Context, splitID int64) ([]Candidate, error)
   }

   type SplitRulesProvider interface {
       GetRules(ctx context.Context, splitID int64) (TeamRules, error)
   }
   ```

   Реализации подставляются в `cmd/api/main.go`. Модуль `member` ничего не
   знает про `distribution` и не импортирует его.

3. **Типы на границе принадлежат потребителю.** `distribution.Candidate` —
   это его собственная структура, а не `member.Member`. Поставщик при
   необходимости конвертирует. Так модули не протекают друг в друга.

4. **`domain.go` не импортирует ничего из проекта** и ничего из инфраструктуры
   (ни pgx, ни chi, ни net/http). Только стандартная библиотека.

5. **`platform` может импортировать кто угодно; `platform` не импортирует
   ничьи модули.** Это единственное исключение из правила про интерфейсы.

6. **Циклов между модулями быть не должно.** Если два модуля нужны друг другу —
   граница проведена неверно, выносите общее в третий модуль или в `domain`.

Автоматической проверки границ нет — держим их на code review. Если добавляете
новую зависимость между модулями — сначала интерфейс в `port.go`, потом код.

### Почему так, а не микросервисы

Распределение одной транзакцией читает участников, анкеты и правила, создаёт
команды и меняет статус. В монолите целостность обеспечивается
`SELECT ... FOR UPDATE`; при разрезании на сервисы потребовались бы саги и
компенсации. Интерфейсы в `port.go` — это тот же контракт, что был бы в gRPC,
только без сети: если модуль когда-нибудь понадобится вынести, меняется
реализация интерфейса, а бизнес-логика не трогается.

## Контракт API

`/api/openapi.yaml` — источник истины. Из него генерируются серверные
интерфейсы (Go) и клиент (фронтенд).

- Сначала правится спецификация, потом код. Не наоборот.
- Изменение спеки — отдельным PR с уведомлением команды: от файла зависят
  фронтендер и тестировщик.
- `internal/api/gen` правится только через `make gen`. Руками — никогда. Сгенерированный код в git не коммитится.
- Handler не изобретает поля: DTO берутся из сгенерированных типов.

Ключевые решения контракта, которые надо держать в голове:

- Правила состава: `teamSize` + `roles[]` с `perTeamMin` / `perTeamMax`.
  Простого списка названий ролей недостаточно — квоты обязательны.
- Анкета **замораживается** при вступлении: `members.form_snapshot` (jsonb).
  Редактирование анкеты после вступления не влияет на распределение.
- Статусы: `Draft → Open → Closed → Finished`. В `Finished` только через
  публикацию распределения.
- `preview` даёт результат без публикации; `publish` фиксирует его.
- Прогон детерминирован: `seed` сохраняется в `distribution_runs`.

## Инварианты предметной области

Нарушение любого из них — баг, даже если тесты зелёные.

**Правила состава (проверять при создании и обновлении пространства):**
```
sum(perTeamMin) <= teamSize <= sum(perTeamMax)
teamSize >= 1
len(roles) >= 1
perTeamMin <= perTeamMax
```
При нарушении — 422 с перечнем конкретных проблем в `details`, а не общее
«invalid request». Без этой проверки алгоритм получит нерешаемую задачу.

**Распределение:**
- Каждый участник ровно в одной команде (или в листе ожидания при
  `remainderPolicy: waitlist`).
- Квоты ролей соблюдены в каждой команде.
- Размеры команд в допуске согласно `remainderPolicy`.
- Один и тот же `seed` на одном составе даёт идентичный результат.

**Идемпотентность публикации:** `publish` и срабатывание таймера одновременно
не создают два набора команд. Реализация: `SELECT ... FOR UPDATE` на `splits`
плюс проверка статуса **внутри** той же транзакции.

**Приватность:** студент не видит анкеты других участников. Список участников
с анкетами (`MemberDetailed`) доступен только владельцу пространства.

## Работа с БД

- Схема только через миграции goose.
- Идентификаторы: `BIGINT GENERATED ALWAYS AS IDENTITY`.
- Именование: `snake_case` везде, без исключений.
- `created_at` / `updated_at` на всех таблицах.
- Запросы — в `internal/<модуль>/sqlc/queries.sql`, типы генерируются через `make gen` (sqlc) в `internal/<модуль>/sqlc/db`; конфиг один — `backend/sqlc.yaml`.
- Транзакции начинаются в `service`, не в `repository`. Репозиторий принимает
  готовый `pgx.Tx` или пул.

Ошибки, которые уже были в исходной схеме и не должны вернуться:
- `members.team_id → teams.id` (не `members.id → teams.id` — это связывало бы
  первичные ключи).
- `members.team_id` и `assigned_role` nullable: на момент вступления команд нет.
- `UNIQUE(split_id, user_id)` в `members`.
- `users.login` — `VARCHAR`, `UNIQUE`.
- У пользователя может быть **несколько** анкет, уникальности по `user_id` нет.

## Ошибки

Единый формат ответа (`Error` в спеке): `code`, `message`, опционально
`details` и `requestId`.

- `code` — машиночитаемый snake_case (`invalid_team_rules`, `already_member`).
- `message` — человекочитаемый, на русском.
- Доменные ошибки объявляются в модуле (`var ErrSplitNotOpen = ...`),
  в HTTP-коды маппятся **централизованно** в `platform`, не в каждом handler.
- Чужой ресурс — 404, а не 403: наличие ресурса не раскрывается. Исключение —
  когда пользователь имеет доступ к пространству, но не является владельцем:
  тогда 403, факт существования ему и так известен.

## Тестирование

- Тесты модуля лежат в `internal/<модуль>/tests/` (внешний пакет `tests`, только экспортируемый API модуля).
- Юнит-тесты — на `domain` и `service` (с подменёнными портами).
- Интеграционные — на `repository` и сквозные сценарии через testcontainers-go.
- Инварианты распределения покрываются property-based тестами на случайных
  входах, а не парой примеров. Это самая ценная часть тестов в проекте.
- Таблично-ориентированные тесты (`tests := []struct{...}`) — стиль по умолчанию.
- Моки пишутся руками в `*_test.go`. Генераторы моков не подключаем.

Автотесты API пишет тестировщик в отдельном проекте (Java, REST Assured).
Ему нужны: стабильный `make seed` и работающий `POST /test/reset`
(только при `APP_ENV=test`). Не ломать их молча — это заблокирует человека.

## Команды

```
make up        # поднять всё (БД + сервис)
make down      # остановить
make migrate   # накатить миграции
make seed      # сид-данные: 1 преподаватель, 8 студентов, 1 пространство
make tools     # установить oapi-codegen и sqlc
make gen       # oapi-codegen + sqlc (результат в .gitignore)
make test      # тесты
```

Конфиг только через env, значения по умолчанию в `.env.example`:
`DATABASE_URL`, `JWT_SECRET`, `PORT`, `APP_ENV`, `CORS_ORIGINS`.

## Стиль кода

- `gofmt`, стандартные идиомы Go.
- Ошибки оборачиваются с контекстом: `fmt.Errorf("create split: %w", err)`.
- `context.Context` первым аргументом везде, где есть I/O.
- Комментарии — почему, а не что. Очевидное не комментируется.
- Комментарии и сообщения коммитов на русском, идентификаторы на английском.
- Коммиты: `feat(split): валидация квот ролей`, указывать модуль в скобках.

## Правила работы в этом репозитории

- Перед добавлением зависимости между модулями — сначала интерфейс в `port.go`.
- Перед изменением поведения API — сначала `openapi.yaml`.
- Не трогать `internal/api/gen` и `internal/<модуль>/sqlc/db` руками.
- Не создавать таблицы в обход миграций.
- Не добавлять библиотеки из списка «не добавлять» без обсуждения.
- Если задача требует нарушить границу модуля — остановиться и сказать об этом,
  а не обходить правило. Скорее всего, граница проведена неверно и её надо
  пересмотреть, а не продавить.

## Что сознательно не сделано

Отсутствует намеренно, не нужно «чинить»: авто-финиш по таймеру (воркер),
ручной перенос участников между командами, пожелания по сокомандникам,
уведомления, rate limiting, внешний стенд. Всё это — после MVP.
